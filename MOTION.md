# HabitCents UI and motion

This pass uses the existing Express/EJS/CSS/browser-JavaScript application and PostgreSQL `pg` data layer. It adds no framework, animation dependency, schema, migration, reminder feature, recurrence rule, or historical denominator.

## Animation preference and refresh replay

- Profile → **Animations** is a native keyboard-operable button with switch semantics, visible focus, and On/Off text. Before any explicit choice it reflects the system preference.
- Precedence: explicit **On** enables app motion even with Windows/browser reduced motion; explicit **Off** renders final values immediately; no valid saved choice follows `prefers-reduced-motion`. Windows settings are never modified.
- The explicit `on`/`off` choice is stored as `habitcents-motion-preference` in localStorage: this browser profile, device and origin only, across refreshes/browser restarts. It is not an account setting or server preference. Storage failure keeps a choice for the current document; the next document falls back to the system. Invalid stored values also fall back to the system. Storage events synchronize other open tabs.
- `motion-preference.js` runs synchronously before styles. Its effective `data-motion` root attribute and `motion-preference.css` control CSS transitions/keyframes (including pseudo-elements); JS numbers, shared progress, charts, dialogs, calendars, habit feedback and navigation all consult that controller. There are no independent reduced-motion CSS overrides blocking explicit On.
- Preference changes apply immediately. Off settles active numeric/progress/donut targets exactly, cancels animation frames and presentation effects, and completes pending dialog closes with timer cleanup. On enables subsequent changes without starting settled entrances again.
- Every **fresh document**, including each refresh and ordinary navigation load, gets eligible visible metric/progress/chart entrances. A cached back/forward document keeps its settled records. Same-target rerenders, unchanged API responses, resize, hover, scrolling and visibility changes never restart entrances. Later values retarget from the current displayed value, retaining synchronized number/fill timelines and exact final values. Offscreen and unavailable values keep their existing behavior.

## Presentation and lifecycle rules

- Business values remain in the API responses/page state. Animations receive copies of numeric targets. They do not write amounts, completion state or schedules.
- Numbers use tabular numerals. Metric accessibility labels and progressbar ARIA values describe the exact source, not each intermediate frame; status regions announce results/errors separately.
- `null`, missing data, failed requests, unsupported history and unset budgets stay unavailable. They are not passed into a zero tween. Errors cancel relevant timelines, preventing a late frame from replacing an error placeholder.
- Visibility is checked against the viewport before starting. Off-screen metrics render at their final value without waiting for an observer or replaying on scroll. Active numeric frames avoid layout measurements; they stop for a hidden/disconnected owner or hidden page. Page exit settles effects and releases motion/visibility listeners; returning cached documents retain final records and bind listeners again without replay.
- Entrance “seen” markers exist only in document memory, never sessionStorage. Metric values and financial data are not persisted by the motion system. Dock navigation still stores a position and pathname in sessionStorage only until the next page.
- FLIP transfers the timeline owner across a replacement with the same record ID and releases records for removed cards. It does not reorder data.
- New date popovers retain native editable date inputs. Their calendar supports arrow keys, Home/End, Page Up/Down, Enter/Space and Escape, with weekday labels, date names, selected/current states and focus restoration. Native date entry remains the fallback when the Popover API is absent.

## Forms and supported habit scheduling

The habit editor separates **Track by** from **Repeat**. Check-off maps to an empty target/unit; quantity preserves an editable numeric target and unit; duration is an explicit minutes-target shortcut with presets and a synchronized editable number/range. The existing persisted `target`/`unit` fields remain authoritative; no new tracking taxonomy is stored. The legacy `check` icon key is presented as Spark, while all saved icon keys remain valid.

Repeat exposes only what the current API persists: every day or selected ISO weekdays. Selected weekdays mean specific scheduled days repeated each week, not a weekly quota. Description/category are optional disclosures. New expense and goal forms keep precise financial inputs, explicit submit labels and reusable selection/date controls. The Dashboard description stays visibly blank and retains `aria-label="Expense description"`.

The following future model needs a separate product/schema decision before implementation:

| Independent dimension | Proposed representation | Outstanding decision |
| --- | --- | --- |
| Recurrence | `frequency: daily/weekly/monthly/yearly`, timezone and effective version | Which period boundaries and week start apply? Existing selected weekdays stay scheduled weekdays. |
| Fulfillment policy | An explicit calendar-period quota, a specific weekday/date schedule, or an elapsed interval anchored to completion | These must be distinct values. For a calendar period, when is an unfinished quota due? For a fixed interval, which completion anchors the next deadline? |
| Tracking | `kind: checkoff/quantity/duration`, target and unit | A future explicit kind may distinguish units such as minutes from a general quantity. The cosmetic pass does not add that column. |
| Universal streak / Today denominator | Existing account-wide daily capture policy and Asia/Dhaka boundaries | Should non-daily quotas be excluded, counted on scheduled/deadline days only, or handled by another explicit rule? No behavior is selected here. |
| Irregular dates | Explicit monthly/yearly scheduled-date policy | Clamp, skip, or another rule for month ends and February 29? Recurring expenses already have their own existing anchor/clamp rules; those do not define habit semantics. |

No weekly-quota/monthly/yearly habit controls were exposed, no closed schedule snapshots were rewritten, and historical completion percentages remain unavailable when no denominator was recorded.

## Profile motion and display preferences

The Profile Animations switch continues to use `HabitMotionPreference`, the existing early root `data-motion` attribute, and the shared CSS motion rules. It does not define a second motion preference. The Profile also stores clock format and display week ordering locally in `HabitCentsPreferences`; this preference layer emits `habitcentspreferenceschange` so the Dashboard clock and weekly strip can update immediately. It does not change ISO dates or habit schedule values.
