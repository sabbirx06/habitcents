# Habits, Expenses and Savings workspaces

## Decisions and preserved behavior

### Approved recurrence integration · 24 October 2026

These approved rules supersede the earlier selected-weekday-only scope below. There is **one account-wide universal streak**. Flexible quotas never contribute to that streak or Today's completion denominator, including on their deadlines. Daily and specifically scheduled occurrences contribute when due. A closed day without required occurrences still resets the streak; a quota-only account earns no streak days.

Tracking and recurrence are independent. Check-off stores one boolean occurrence per date. Count stores a nonnegative whole-number achieved total for that date. Measure stores a nonnegative amount and unit, including minutes/hours. Numeric input **replaces today's total**; it never adds an increment. Daily check-offs and daily/selected-weekday quantitative habits retain their existing semantics. History remains read-only. Existing numeric habits with no explicit tracking metadata are interpreted as measured totals; no stored values are converted.

Recurrence supports every day, selected ISO weekdays, and weekly/monthly/yearly calendars. The latter support either flexible quotas within the calendar period or a specific weekday/date. Selected weekdays remain individual scheduled occurrences, not quotas. Elapsed-after-completion intervals are deferred. Weeks are Monday–Sunday, months/years are calendar months/years, all in Asia/Dhaka. Profile week start is display-only. Date anchors clamp to the last valid day without shifting the anchor (31 January → 28/29 February → 31 March; annual 29 February → 28 February in ordinary years).

New flexible quotas offer **Start this period** (full target for the remaining period, explicitly not prorated) and **Start next period**. The default is next period except on the first day of the period. The form shows concrete activation and deadline dates. Before activation there is no required/incomplete/missed quota in summaries or reviews. No carryover or advance credit occurs. A quota is missed once its calendar period closes without the target; history/reviews evaluate this from stored dates and totals, with no browser timer or background job.

Quota edits, including changes into/out of quota scheduling, are stored as a pending version effective at the next boundary of the current quota (or the requested quota when converting from a daily/scheduled habit). Re-editing replaces the pending version, not the active one. Creation metadata/icon/color/name can update immediately. Daily/selected-weekday and specific-date edits apply today; closed versions stay unchanged. Archive/restore retain the existing today-effective behavior and preserve logs and future schedule changes. Archive/restore and edits cannot activate a not-yet-started quota. Deletion remains explicit and removes owned habit logs under the existing contract; closed universal snapshots retain captured identities.

`public/js/recurrence.js` shares calendar calculations across the browser, recurrence service and reviews. `lib/habit-service.js` resolves active/pending versions rather than assuming the current `habits` metadata describes a closed period. `habit_schedule_versions` is the authority for requirements; unknown legacy history stays unknown. Current-period progress sums dated records only within that quota window. Check-off quotas have a target of one occurrence; use Count for multiple occurrences or Measure for an amount. Changing today's entry downward can reverse current-period fulfilment.

Habit mutation transactions lock the owned user row, serialize progress and schedule changes, and capture the universal day before commit. `(habit_id,date)` and `(habit_id,effective_on)` uniqueness enforce set-total/version idempotency. Streak values are derived, never incremented per completion. Captures include known future rules so missed scheduled occurrences and pending changes evaluate correctly across unvisited days. Old snapshots without recurrence rules retain their original weekday evidence. No enrollment, historical DATE, or old success is backfilled.

The existing editor now separates Check-off / Count / Measure from Repeat, with conditional quota/date fields, duration presets, editable targets, icon/color selection and a save summary. Dashboard daily rows contain only due scheduled occurrences; its separate current-quota disclosure links to progress in Habits. Numeric completion opens the existing progress dialog. The latest single-checkmark and motion controls remain in place.

- Express/EJS/CSS/browser JavaScript and PostgreSQL remain in place. The attachment's MySQL wording described an older stack; retaining PostgreSQL was confirmed.
- Habit schedules use selected ISO weekdays (Monday 1 to Sunday 7), with all days as the creation default. Quantitative entry **sets that day's total**, not an increment. No weekly-quota feature was invented after the clarification to use chosen weekdays/all days.
- The application day is Asia/Dhaka. The PostgreSQL pool sets its connection timezone; new workspace day queries also use the explicit zone. The Dashboard's clock/calendar continue to show browser-local time. Existing streak enrollments with another timezone remain unavailable pending explicit review, rather than reinterpreting snapshots.
- One universal streak counts completed scheduled days, not difficulty points. An unfinished current day is not a missed day. A closed incomplete day or closed day with no required habits resets the streak, following the previously confirmed policy. Adding/editing/archiving changes today's requirements. Closed snapshots remain evidence even after deletion.
- Quantitative targets, schedule and archive changes are versioned from their effective day. Legacy creation dates remain NULL. Old completion logs are shown as real completions; missing legacy logs remain unknown. The migration records only the schedule known on installation day.
- Historical habit inspection is read-only. Corrections were optional in the requirements and have not been added; no current-day mutation endpoint accepts a past date.
- Active savings means **not archived**. Completed goals remain in that set until explicitly archived; their balances are preserved. Rings clamp visually to 0–100%; actual saved/target values retain precision. Withdrawals, contribution-history pages, trends and transfers were not added.
- Recurring definitions do not create transactions. Confirmation locks the owned definition and checks the expected scheduled date. The recorded payment and next-due update commit together. Repeating confirmation cannot create a duplicate payment. Monthly/yearly recurrence retains the starting day, clamped to shorter months; editing a definition does not recreate paid cycles.

### Timezone resolution

The configured URL selects the shared pooler on port 5432. The URL does not override `options`; `pg.Client.connectionParameters.options` actually contains the Dhaka request, while the inspected SQL connection reports UTC. Thus the mismatch occurs after Node's startup configuration; the hosted pooler's exact internal handling/version was not observable. Port 5432 indicates the shared session-pooler convention, rather than proof of transaction mode. See the official [connection terminology](https://supabase.com/kb/troubleshooting/supavisor-and-connection-terminology-explained-9pr_ZO) and [Supabase timezone defaults](https://supabase.com/docs/guides/database/postgres/configuration).

Habit day queries, Dashboard/legacy check-ins, streak reads/captures/enrollment, and current monthly budget/spending queries now explicitly use `(CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Dhaka')::date`. No session `SET`, database timezone setting, pooler configuration, browser display timezone, stored DATE or enrollment value is changed to hide the mismatch. Calendar DATEs remain strings (`pg` type 1082 parser plus explicit `::text` route projections). The operator-only demo seed now defaults its own transaction to Dhaka for future disposable fixtures; it was not run live and cannot rewrite an enrolled account.
