# Habits, Expenses and Savings workspaces

## Decisions and preserved behavior

- Express/EJS/CSS/browser JavaScript and PostgreSQL remain in place. The attachment's MySQL wording described an older stack; retaining PostgreSQL was confirmed.
- Habit schedules use selected ISO weekdays (Monday 1 to Sunday 7), with all days as the creation default. Quantitative entry **sets that day's total**, not an increment. No weekly-quota feature was invented after the clarification to use chosen weekdays/all days.
- The application day is Asia/Dhaka. The PostgreSQL pool sets its connection timezone; new workspace day queries also use the explicit zone. The Dashboard's clock/calendar continue to show browser-local time. Existing streak enrollments with another timezone remain unavailable pending explicit review, rather than reinterpreting snapshots.
- One universal streak counts completed scheduled days, not difficulty points. An unfinished current day is not a missed day. A closed incomplete day or closed day with no required habits resets the streak, following the previously confirmed policy. Adding/editing/archiving changes today's requirements. Closed snapshots remain evidence even after deletion.
- Quantitative targets, schedule and archive changes are versioned from their effective day. Legacy creation dates remain NULL. Old completion logs are shown as real completions; missing legacy logs remain unknown. The migration records only the schedule known on installation day.
- Historical habit inspection is read-only. Corrections were optional in the requirements and have not been added; no current-day mutation endpoint accepts a past date.
- Active savings means **not archived**. Completed goals remain in that set until explicitly archived; their balances are preserved. Rings clamp visually to 0–100%; actual saved/target values retain precision. Withdrawals, contribution-history pages, trends and transfers were not added.
- Recurring definitions do not create transactions. Confirmation locks the owned definition and checks the expected scheduled date. The recorded payment and next-due update commit together. Repeating confirmation cannot create a duplicate payment. Monthly/yearly recurrence retains the starting day, clamped to shorter months; editing a definition does not recreate paid cycles.

## Files and routes

Shared workspace UI: `public/css/workspaces.css`, `public/js/workspace.js`. Three page templates and their browser modules use existing canvas/surface/ink/blue/lavender tokens and the floating dock. Modals use native dialog modality, a blurred/dim backdrop, focus restoration, a visible Close action, Escape/backdrop dismissal, scroll locking and reduced-motion support.

`lib/workspaces.js` registers authenticated `/api/` routes for habits/history/categories/presets, monthly expenses/budgets, recurring definitions/confirmation, and savings goals/contributions. Inputs and calendar dates are validated and SQL values are parameterized. Every record lookup/mutation is scoped to the session user. Dynamic SQL branches contain only fixed, server-owned column text.

The existing Dashboard presentation is retained. Small compatibility changes filter archived/rest-day habits and archived goals, respect explicit false/partial check-ins, keep current totals synchronized, and refresh after another tab changes shared data. The former production demo streak fallback was removed: unavailable normal-mode tracking is never replaced with 7. Clearly labeled preview fixtures still provide recorded demo streaks.

Legacy `/categories` navigation redirects into the integrated preset browser. Destructive legacy GET reset routes now redirect without changing data. Budget editing uses upserts and never deletes transactions. Existing goal and expense endpoints also reject invalid/negative contributions or expenses. User-provided text is rendered as text nodes, not inserted into HTML templates.

## Migration review and activation — not applied to live data

1. Inspect which migrations and columns already exist, back up the database, and review SQL against that installation. `schema.postgres.sql` remains the initial empty-database schema, not an upgrade/reset script.
2. Review existing category support (`001-expense-categories.sql`) and universal streak storage (`002-universal-streak-draft.sql`). Do not blindly rerun already-installed migrations.
3. `003-workspaces.sql` adds descriptions/icons/colors, nullable creation/archive dates, selected weekdays and optional targets; quantitative daily progress; forward schedule versions; owned habit categories; goal deadlines/archives; recurring definitions and unique scheduled-payment linkage. Existing IDs, difficulty values, check-in logs, expenses and saved amounts are preserved. No historical scheduling or streak success is backfilled.
4. `004-sessions.sql` adds persistent production sessions. Production startup refuses an in-memory session store. HTTPS cookies are HttpOnly, SameSite=Lax and Secure in production. Set `TRUST_PROXY=1` only for a trusted single proxy. Deployment, session-expiry cleanup policy, credentials and infrastructure remain operator responsibilities; no deployment was performed.
5. Verify the migrations locally with `node --test test/workspaces.test.js`. These tests create isolated PGlite databases, execute the actual SQL, and verify preservation, ownership, precision, schedule/streak integration and payment deduplication. They never connect to `.env` or a live database.
6. Apply reviewed migrations through the separately authorized deployment/database workflow, not through page loads. New metadata-dependent mutations report a setup/migration error when storage is absent. Existing habit/goal reads, real historical completions, binary check-ins, expense budgets/transactions and contributions remain readable/usable before the optional metadata upgrade.
7. A user without an enrollment may explicitly choose **Start tracking today** on Habits after the storage is installed. This creates a forward-only enrollment and initial snapshot atomically. Existing enrollments are never overwritten by this action; timezone/history review is required for them.
