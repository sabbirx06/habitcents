# Dashboard additions: categories and habit continuity

The existing dashboard now includes a category spending breakdown, muted category-colored recent/historical expense rows, an optional category selector, and a bounded per-habit contribution grid. Its inverse local-time header, week/date navigation, floating dock, Neue Haas typography, budget calculations, read-only history, check-ins and savings ring remain in place.

## Required category setup

For an **existing local PostgreSQL database**, apply `migrations/001-expense-categories.sql` using the existing local database tooling. This additive migration adds a checked `expenses.category` column with default `uncategorized`. It preserves existing amounts, dates and descriptions and can be applied repeatedly. It was tested only in isolated PGlite databases. It was **not applied to Supabase or any live database**.

For a new empty database, `schema.postgres.sql` already includes the column and constraint. Do not rerun that full creation script against an existing database.

Classified writes require this migration. Before it is applied, the application continues to read older expenses as Uncategorized and can save uncategorized entries. A classified submission returns an explicit HTTP 503 setup message and does not save a transaction with its category discarded. Production category functionality has not been verified and must not be considered ready until its schema setup is authorized and applied.

Allowed categories: Transport, Food, Subscriptions, Shopping, Uncategorized. Categories are supplied explicitly; descriptions are never used for inference. One dashboard mapping supplies the muted category tints and legend swatches.

## Data contracts

- `GET /dashboard-breakdown?month=YYYY-MM` or `?date=YYYY-MM-DD`: exactly one strictly validated range. Returns explicit inclusive start/end, month/day kind, exact decimal total and exact grouped category amounts. The frontend verifies category totals reconcile in integer cents. Today mode requests the browser's current calendar month; history requests the selected day. The existing budget's server-day semantics are unchanged, and the breakdown always labels its own date range.
- `GET /dashboard-continuity?habitId=…&end=YYYY-MM-DD`: validates the date and habit identifier, verifies authenticated ownership, then returns true completion records in a bounded 12-column Monday-aligned range. Stored DATE values remain calendar strings. The response includes start/end and server current date; future completion records are not reported as completed dates.
- Both endpoints and all expense/history queries are user-scoped and parameterized. Independent client request generations prevent earlier date/habit selections from overwriting the latest selection. Each module has its own loading, empty, error and retry states.

The schema has no habit creation dates, historical schedules or name snapshots. The endpoint therefore returns `createdDate: null` and `streak: null`. The UI shows recorded completions and unrecorded dates, never inferred misses, historical habit totals or invented streaks. Future dates are distinct and disabled. In historical mode, the range ends at the selected day; later positions are blank padding without dated cells. Support for known creation dates is tested in the client, but the normal server does not fabricate them. Deleted habits/logs and deleted expenses cannot be reconstructed.

The continuity section now always contains two cards. Each builds its bounded 84-position calendar locally before habit/history requests resolve, independently of the financial summary. Each card has a habit selector and independent request generation and retry. With fewer than two habits, the remaining card retains a neutral shell and an Add a habit link. `GET /dashboard-spending?end=YYYY-MM-DD` is authenticated, read-only, strictly date-validated and user-scoped. One parameterized SQL statement returns grouped daily decimal sums/counts and a matching window total for the month through the supplied end date. It needs no category migration. The client requests the browser's current month through today, or the selected month through the selected date, capped at actual local today. Future months have no elapsed-date series.
